## PrefabSpawnSystem ported from the Beef side (2026-09-19)

Their eb4bc82f was the cleaner answer to a question we had open (how a script spawns a
prefab without the surface seeing the content database), and it exposed two defects in
ours, so it came over (c59ff8ec). A scene system in the full composition (module `prefabs`,
count 12) holds the content database + resource manager; DefaultApplication is an
ISceneObserver now and points every composed scene's system at them at SystemsReady, and
re-points live scenes when the database or the manager arrives later (both can land after
scenes exist). Spawn(prefab, position, rotation, parent) reads the payload, spawns it with
the database as the nested-payload resolver, places the root in the parent's space, binds
the spawned subtree only (new `SceneSystem::ResolveEntityResources(entity, manager)` hook,
`SerializableComponentManager` implements it, free `ResolveEntityResources(scene, root,
manager)` walks the subtree). Every failure is an invalid handle, never a partial spawn.
What it replaced: the recipe twice in DefaultApplication (script spawner lambda +
ResolveNetworkPrefab), NEITHER passing a nested resolver - a runtime-spawned template's
nested instances were silently absent for scripts and replication alike - and both
re-walking every ref in the scene per spawn. The script path lost three indirections:
`scene.spawn` reaches the scene's own system; `ScriptRuntimeBinding::spawnPrefab`,
`ScriptSubsystem::SetPrefabSpawner` and the live wrapper are gone. ResolveNetworkPrefab
stays (tested name) and delegates to the static SpawnInto.
Tests: PrefabSpawnSystemTests (placement under a parent with rotation + children,
subtree-only binding through a real ResourceManager, the NESTING regression, every failure
path); the six script spawn tests run the real recipe over a one-prefab database (the
fake callback seam is gone with the seam); SceneSurfaceTests pins 12 modules + presence.
Four lanes green, 153/153 each. Docs: text-scenes (the touch point), scripting,

## GPU picking (2026-09-21)

Asked for, with legacy Sedulous `PickPass.bf` (branch master) as the reference and "make it
better if you can". Legacy: an on-request pass rendering every mesh at full resolution into an
RGBA8 target (entityIndex + 1 in the colour), one pixel copied to a 4-byte staging buffer, a
fixed two-frame wait, `RequestPick` / `TryGetResult`. Ours keeps that shape and changes four
things: the camera projection is CROPPED to the requested rect so a click renders a 1x1 target
(vertex work only; the terrain chunk cull runs against the crop); the target is `RG32Uint` with
(index + 1, generation) so a hit is an exact `EntityHandle`; the readback retires on the device
ring's round trip (the ThumbnailStage rule) instead of a fixed wait; and rect requests answer
unique hit sets (the marquee's substrate). It rides the depth-only caster path in every renderer
(`Renderer::ResolvePickIds`, default no-op): static, skinned, instanced and MultiMesh meshes and
terrain, masked cutouts kept, two-sided materials picking both faces. Requests key on the
`RenderScene` viewport key so only that view answers. Bugs met: `entityId` lived on
MeshRenderData (moved to the RenderData base - every producer tags); WebGPU validates a bound
uniform range against the shader's declared cbuffer, so the shadow-view ring's bind range became
the PickView size (80). The select tool asks the GPU on click and applies the answer when it
lands, CPU origin pick as the fallback. Docs in renderer.md 9.x + editor.md 3.6. Pack re-cooked.
Proof on Vulkan + WebGPU + the cooked WGSL path, plus the device-free halves; four lanes.

## Texture import: the batch dialog's Import gate never opened (user report 2026-09-21)

"Import, pick a texture, click Import, nothing happens." Reproduced under gdb with the user

## Simulate crash: a dynamic body over a mesh shape (user report 2026-09-21)

Reproduced under gdb with the user driving the project manager: Simulate -> BuildBodies ->
PhysicsWorld::CreateBody -> Jolt's "Invalid mass" assert (SIGTRAP). Triangle meshes, planes
and heightfields derive no mass in Jolt, and a mass override only moves the failure to the
first contact with another mesh ("Unsupported shape pair" - found by the first cut of the
fix, which gave such bodies a bounds-box mass). Ruling: a dynamic body needs a convex shape;
the world demotes a dynamic body over a non-convex shape (mesh/plane/heightfield, also inside
a compound or a scaled shape) to STATIC with an error, and the subsystem names the entity for
the kinds it can see. A convex shape degenerate to zero volume keeps the bounds-box mass
fallback. Physics.Tests covers mesh, plane and compound demotion with a box still falling
through the same world. physics.md rule added.
The Beef agent fixed the same crash the same day (their 34fb4ce8: Jolt's own
`Shape::MustBeStatic()`, demoting ANY non-static motion - a kinematic mesh asserts too, which
the first cut here missed). Both assessments agreed; the merged fix shipped here for them to
take: MustBeStatic as the predicate, dynamic and kinematic demoted, every case named at the
entity (cooked meshes via the resource's `convex` flag), the flat-hull mass fallback kept with
its rationale corrected (Jolt refuses zero scale at shape creation, so the flat hull is the
one reachable degenerate), tests for mesh, plane, compound, kinematic, heightfield-with-a-ball
and the flat hull.

## DDS import: pass-through with a decode fallback (user request 2026-09-22)

The Bistro package ships BC-compressed DDS textures and nothing read DDS. Route chosen: a DDS
is a GPU-ready container, so its levels should reach the cooked texture untouched, with a
decode only where they cannot. New `foundation.image.dds` (Foundation/Image.DDS): both header
forms (legacy FourCC + DX10), `LoadDds` keeps the payload bytes layer-major, `DecodeLevel` runs
bcdec (promoted from test-only; the module is its one implementation site) to RGBA8 / RGBA32F
with BC5 given a reconstructed Z, `WriteDds` emits the DX10 form. Image.IO's loaders sniff the
magic, so thumbnails, pages and model loaders read a DDS as its level 0 without a change.
The texture builder passes levels through when the target reads BC, compression is not None,
the block format fits the usage (Colour BC1/2/3/7, Normal BC7 only - the BC5 shader rule
stands, Mask BC4/BC7, HDR BC6H) and the chain is there when mips are wanted; else it decodes
level 0 and cooks as an image (ASTC, None, BC5 normals, chain-less files). The importer accepts
.dds and reads the header's facts (BC5 = normal, BC4 = mask, float = HDR, a DX10 colour space).
A model referencing DDS keeps them on disk: the loaders leave a DDS undecoded
(`ModelTexture::sourceFile`), the importer copies it into Sources/ as a file-backed asset with
the slot's usage, and the direct cook path decodes from the file. Tests: 10 container / decode
cases, 4 pipeline cases (byte-identical pass-through, twin by colour space, level-0-only, None,
BC5 -> BC7 + generated mips, ASTC target, cubemap refusal), importer presets, and a generated
glTF whose BC1 albedo passes through the cook driver. Not yet: cubemap / array / volume DDS.

Bistro itself (the RTXDI glTF: 390 DX10 BC7 DDS with full chains, every one pass-through)
needed two more glTF loader facts: its textures name a PNG `source` and carry the DDS under
`MSFT_texture_dds` (the loader now prefers that image), and its materials are
`KHR_materials_pbrSpecularGlossiness` (diffuse map / factor stand in for base colour,
glossiness inverts to roughness, dielectric; the specular map is not converted). The generated
test glTF uses both shapes. FBX references get the same undecoded-DDS treatment through one
resolver; an FBX with the DDS EMBEDDED still decodes level 0 (no file to point at).
A model-relative uri keeps its path under Sources/ and reuses the .gltf sidecar copy (the
first run copied every DDS twice: 4 GB for a 2 GB package).

Measured through the headless MCP host (`asset_import` + `asset_cook`, clang debug): Bistro
imports in 39 s and cooks all 1149 assets (1 manifest, 551 meshes, 254 materials, 343
textures) in 65 s with 0 failures at 221 MB peak; every one of the 343 cooked texture payloads
is byte-identical to its DDS past the header.

## Editor main-thread stalls: thumbnails and the import (user, 2026-09-23)

Two stalls the user hit in RTHomes1. Thumbnails: `IThumbnailGenerator::Prepare` read every

precedes the envelope so the XML sees the final chain). Main-thread share: 16.3 s -> 0.9 s; the

## Texture cook: 506 s -> 7 s for six 4k textures (user question, 2026-09-23)

"How long should just those 3 or 4 textures per pack really take to import and cook?" Import:
10-70 ms each. Cook, measured through the MCP tool on the RTHomes1 4k JPEGs: 506 s for six, 84 s
per texture on one core - the whole thing serial and at -O0, with the mid BC7 effort. Now 1.2 s
alone (decode 0.2, mips 0.1, BC7 0.8) and 7.4 s for six on 16 cores. The four causes, each now a
rule: (1) `EncodeBlockCompressed` fans block rows out over the cook's job system
(`AssetBuildContext::jobs`; the MCP tool's cook gained a job system too, it was hard-coded
serial), and the mip filter fans its rows out the same way; (2) the vendored encoders and the
stb bodies compile at -O2 in Debug (CONVENTIONS); (3) Default compression maps to bc7enc's uber
0, Quality to uber 4 (the mid level was ~4x the cost for a fraction of a dB); (4) `Array::Resize`
reserved the exact size and relocated element by element - the 85 MB mip chain reallocated per
level, 6 s at -O0 - and now grows 1.5x on a growing resize, relocates trivially copyable
elements as one block and zero-fills trivial growth (the first resize from empty stays exact).
The mip filter's sRGB transfer runs through per-chain tables instead of Pow per texel. The
builder logs each texture's decode / mips / compress / write split and the driver logs each
build's time. Tests: the fan-out is byte-identical to the inline encode for every BC format;
the array's growth, relocation and zero fill.

## Bistro prefab open: the settle-reload stall (user, 2026-09-23)

"Another thing that was slow/blocking was opening Bistro prefab." Instrumented first: the
scene page logs `opened scene 'x': parse / bind / prefabs ms (UI thread)`, the context logs
each page open, and `ResourceManager::Pump` logs every finalize past 50 ms (type + id) and each
burst once when its pending set drains. The 49 MB XML prefab (1071 cooked products, 2.1 GB)
opens in 2.9 s on the UI thread (parse 2.7 s, the async binds 0.2 s) - and then the log showed
148 finalizes past 50 ms, the tail climbing from 0.5 s to 8 s as a stack unwound. The chain: a
texture settles, its material reloads through the dependency edge in the caller's SYNC mode,
the reload sync-binds the material's other pending textures, and a sync bind of a pending id
waited out the decode and then ran an unbounded Pump that finalized everything decoded so
far - which reloaded more materials, nested. One 8 s stall. Two fixes: the dependents' reload
runs with async binds on (pending slots stay skipped, each settle reloads again), and a sync
upgrade finalizes its own id only; the rest keep their FIFO turn. Alongside: the binary
serializer moves scalar arrays as one block (`ISerializer::BulkScalarArrays`, byte-identical
to the per-element layout, so no data version moves). Not chased, per the user: Debug-only
shader compiles and pipeline creation under validation, which the finalize line now names by
type. Tests: the reload leaves the other child pending and fills it on its own settle; the
single-id upgrade; bulk scalar arrays byte-identical and round-tripping; the burst report once
per burst and the slow-finalize line by threshold. Follow-up (backlog): the XML parse is now
the UI-thread cost of a large source scene.
