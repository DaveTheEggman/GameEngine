## PrefabSpawnSystem ported from the Beef side (2026-09-19)

Their eb4bc82f was the cleaner answer to a question we had open (how a script spawns a
prefab without the surface seeing the content database), and it exposed two defects in
ours, so it came over (c59ff8ec). A scene system in the full composition (module `prefabs`,
count 12) holds the content database + resource manager; DefaultApplication is an
ISceneObserver now and points every composed scene's system at them at SystemsReady, and
re-points live scenes when the database or the manager arrives later (both can land after
scenes exist). Spawn(prefab, position, rotation, parent) reads the payload, spawns it with
the database as the nested-payload resolver, places the root in the parent's space, binds
the spawned subtree only (new `SceneSystem::ResolveEntityResources(entity, manager)` hook,
`SerializableComponentManager` implements it, free `ResolveEntityResources(scene, root,
manager)` walks the subtree). Every failure is an invalid handle, never a partial spawn.
What it replaced: the recipe twice in DefaultApplication (script spawner lambda +
ResolveNetworkPrefab), NEITHER passing a nested resolver - a runtime-spawned template's
nested instances were silently absent for scripts and replication alike - and both
re-walking every ref in the scene per spawn. The script path lost three indirections:
`scene.spawn` reaches the scene's own system; `ScriptRuntimeBinding::spawnPrefab`,
`ScriptSubsystem::SetPrefabSpawner` and the live wrapper are gone. ResolveNetworkPrefab
stays (tested name) and delegates to the static SpawnInto.
Tests: PrefabSpawnSystemTests (placement under a parent with rotation + children,
subtree-only binding through a real ResourceManager, the NESTING regression, every failure
path); the six script spawn tests run the real recipe over a one-prefab database (the
fake callback seam is gone with the seam); SceneSurfaceTests pins 12 modules + presence.
Four lanes green, 153/153 each. Docs: text-scenes (the touch point), scripting,
game-instance, game-ready-scripting.
Kept our facade signature (`spawn(prefab, x, y, z)`); rotation + parent are on the system,

## GPU picking (2026-09-21)

Asked for, with legacy Sedulous `PickPass.bf` (branch master) as the reference and "make it
better if you can". Legacy: an on-request pass rendering every mesh at full resolution into an
RGBA8 target (entityIndex + 1 in the colour), one pixel copied to a 4-byte staging buffer, a
fixed two-frame wait, `RequestPick` / `TryGetResult`. Ours keeps that shape and changes four
things: the camera projection is CROPPED to the requested rect so a click renders a 1x1 target
(vertex work only; the terrain chunk cull runs against the crop); the target is `RG32Uint` with
(index + 1, generation) so a hit is an exact `EntityHandle`; the readback retires on the device
ring's round trip (the ThumbnailStage rule) instead of a fixed wait; and rect requests answer
unique hit sets (the marquee's substrate). It rides the depth-only caster path in every renderer
(`Renderer::ResolvePickIds`, default no-op): static, skinned, instanced and MultiMesh meshes and
terrain, masked cutouts kept, two-sided materials picking both faces. Requests key on the
`RenderScene` viewport key so only that view answers. Bugs met: `entityId` lived on
MeshRenderData (moved to the RenderData base - every producer tags); WebGPU validates a bound
uniform range against the shader's declared cbuffer, so the shadow-view ring's bind range became
the PickView size (80). The select tool asks the GPU on click and applies the answer when it
lands, CPU origin pick as the fallback. Docs in renderer.md 9.x + editor.md 3.6. Pack re-cooked.
Proof on Vulkan + WebGPU + the cooked WGSL path, plus the device-free halves; four lanes.

## Texture import: the batch dialog's Import gate never opened (user report 2026-09-21)

"Import, pick a texture, click Import, nothing happens." Reproduced under gdb with the user
driving: the click never reached the dialog's handler because the Import button was

constructor, before the owner assigns DescribeFile and describes the files; only the worker

## Simulate crash: a dynamic body over a mesh shape (user report 2026-09-21)

Reproduced under gdb with the user driving the project manager: Simulate -> BuildBodies ->
PhysicsWorld::CreateBody -> Jolt's "Invalid mass" assert (SIGTRAP). Triangle meshes, planes
and heightfields derive no mass in Jolt, and a mass override only moves the failure to the
first contact with another mesh ("Unsupported shape pair" - found by the first cut of the
fix, which gave such bodies a bounds-box mass). Ruling: a dynamic body needs a convex shape;
the world demotes a dynamic body over a non-convex shape (mesh/plane/heightfield, also inside
a compound or a scaled shape) to STATIC with an error, and the subsystem names the entity for
the kinds it can see. A convex shape degenerate to zero volume keeps the bounds-box mass
fallback. Physics.Tests covers mesh, plane and compound demotion with a box still falling
through the same world. physics.md rule added.
The Beef agent fixed the same crash the same day (their 34fb4ce8: Jolt's own
`Shape::MustBeStatic()`, demoting ANY non-static motion - a kinematic mesh asserts too, which
the first cut here missed). Both assessments agreed; the merged fix shipped here for them to
take: MustBeStatic as the predicate, dynamic and kinematic demoted, every case named at the
entity (cooked meshes via the resource's `convex` flag), the flat-hull mass fallback kept with
its rationale corrected (Jolt refuses zero scale at shape creation, so the flat hull is the
one reachable degenerate), tests for mesh, plane, compound, kinematic, heightfield-with-a-ball
and the flat hull.
