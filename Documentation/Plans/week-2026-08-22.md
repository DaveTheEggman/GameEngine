## Seeded: editor extensibility seams (user ruling 2026-08-18: "ultimately must fix")

Origin: navigation P4b-3 (Documentation/Specs/navigation-editor-ui.md, the
FOLLOW-UP + RE-RULING sections). Building nav's Bake button + zone gizmo
surfaced that the editor's per-domain surfaces are NOT plugin-extensible -
every domain couples into Editor.Scene's central dispatch:

- `InspectorViewImpl.cpp` is a hardcoded per-type chain (physics settings,
  RigidBody, the ref-picker table, ...) that grows a direct domain import per
  entry.
- `GizmoRendererRegistry` is per-ScenePage and populated only by
  `RegisterBuiltinGizmoRenderers` inside Editor.Scene - no external hook.

Nav landed as (B) (join the central dispatch - correct for one consumer, per
the re-ruling), but the user has ruled the seams ARE coming; this supersedes
the "second consumer pays for it" promotion rule as a scheduling decision (the
DESIGN of the seams should still be validated against the by-then-real
consumers, nav + whatever else has landed).

Scope for the week:

1. **Inspector per-component action-row registry** - keyed by component type;
   Editor.Scene consults it after (or within) the central chain. First
   migrations: nav Bake (from the (B) placement), and reflection-probe re-bake
   if/when it exists. Outcome flashing stays (no silent success).
2. **External gizmo-renderer registration** - a hook so ScenePage adds
   domain-registered renderers after the built-ins (the per-page registry
   instantiation is the wrinkle: registration must be a provider list the page
   consults, not a global mutable registry).
3. **Migrate Editor.Navigation onto both**; Editor.Scene drops its nav
   imports. `RegisterNavigationEditor(context, host)` returns as the
   per-domain registrar (the shape the original P4b ruling described).
4. **Audit (stretch)**: which existing central InspectorView entries
   (ref-picker table dispatch, per-type sections) should ride the same
   mechanism vs stay central. Produce the list; migrating them is NOT this
   week's scope unless trivially mechanical.

Constraints carried from the rulings: registries follow the house composition-
root style (explicit registration from a registrar function, count tripwires
where a lost registration would fail silently); headless tests for both
registries + the nav migration; both compilers green per landing.

## Seeded: an authored editor sample project (user decision 2026-08-18)

Origin: navigation P5. The demo samples (WebScene, Sandbox, ...) are all
CODE-FIRST and RUNTIME-ONLY - they author scenes in C++ and cook resources
inline. Nothing exercises the EDITOR/authoring side end to end. Add a committed
editor SAMPLE PROJECT - the editor-side equivalent of WebScene/Sandbox - that a
developer opens in the editor and that demonstrates the WHOLE pipeline, not just
navigation: asset import + cook, scene authoring, prefabs, and the subsystems
(render, physics, audio, particles, navigation, scripting, ...) as authored
content rather than code.

Value: a living regression + demo of the authoring stack (import dialogs, the
cookers, inspector, gizmos, the navigation Bake button, play-in-editor) that no
code-first sample covers. It also becomes where new editor features get dogfooded.

Notes / open questions for week start:
- Where it lives: a tracked project dir (NOT the user's untracked EditorProject/
  at the repo root - see the never-git-add-all + test-scratch memories). A
  Samples/EditorProject or Documentation/Samples location, committed.
- Scope creep risk: start SMALL (one scene touching a few subsystems incl. a
  baked nav zone) and grow it; do not try to demo everything at once.
- Nav's slice of it: author a zone, assign a NavigationZoneAsset, Bake, and a
  few agents - the on-screen counterpart to P5's inline-bake code sample (A).
