## Data root unified (2026-09-15)

Asked by the Beef port: "can Raptor unify the data-root walk everywhere and drop the
hard-coded and baked paths, so Sedulous ports one mechanism?" Ruling agreed: the application
resolves the root ONCE (`--data-root` validated, else the `Data/.dataroot` walk from the exe
then the cwd), mounts a native filesystem over it, and hands `vfs::IFileSystem&` to whatever
reads engine data; the engine `Context` knows nothing; no root = a loud error and exit, never a
compile-time fallback. Written up in `Documentation/Systems/data-root.md`.

Built:
- `foundation.vfs`: `ResolveDataRoot` (override validated) + `DataRootFromArguments`; the
  no-root message is an error naming the search and the flag.
- `foundation.shaders`: `IShaderIncludeResolver` + `CompileOptions::includeResolver` - a custom
  DXC include handler (no `-I`, no disk); `FileShaderSourceProvider` is now
  `Initialize(IFileSystem&, folder)` and doubles as the resolver (folder-first, nested includes
  carry their directory); `ShaderSystem::SetIncludeResolver` replaces `SetIncludePaths`;
  `ShaderSystemHost::Initialize(device, dataFileSystem)` with the layout constants
  `kShaderFolder` / `kShaderPackPath` - the pack is read from `Shaders/shaders.dpak` in the
  mount only (the exe-dir/cwd probing is gone).
- Consumers: `RenderSubsystem`, `UISubsystem` (also the built-in Roboto via
  `LoadFontFromMemory` from the mount; `SetFontPath` / `SetUIFontPath` deleted), `ImguiSubsystem`,
  `UIHost` take the mount. `DefaultApplication` owns it (`SetDataRoot` / `DataRoot()` /
  `DataFileSystem()`); `PlayerMain` passes `--data-root`; `WebMain` fetches
  `Data/.dataroot` + `Data/Shaders/shaders.dpak`. Editor: main resolves or exits,
  `EditorAppConfig::dataRoot`, the embedded runtime gets the same root, `BaselineAssetPath` is a
  data path. Export: `ExportOne` / `ExportAll` take `dataRoot`, `StageShaderPack` writes
  `Data/Shaders/shaders.dpak` + `Data/.dataroot` (the dist is a data root); `Tools.Export` and
  `Tools.Mcp` (`RegisterProjectExportTool`) resolve theirs. `SampleApp` resolves from argv;
  every sample and every test that had a baked path reads the data root instead
  (`AudioPlayground`'s wavs moved to `Data/Assets/audio/playground`; the web sample builds
  preload the `Data/` layout). Every `BUILTIN_*` / `SAMPLE_*_DIR` / `TEST_*` define is gone
  except `BUILTIN_PLAYER_BASENAME` (a name, not a path).
- Host fix found on the way: `ApplicationHost::Start` set running AFTER `Configure`/`OnStartup`,
  so an exit requested during startup (unreadable dist, no data root) was overwritten. Now
  running is set before `Configure`, with a test.
- Tests: VFS (override/args), Shaders (resolver-served includes incl. nested + a miss),
  Shaders.System (subfolder scan, mount-relative reload, host over a scratch data root),
  Runtime.Client (startup exit), Editor.Core export (dist carries `Data/.dataroot` +
  `Data/Shaders/shaders.dpak`, staged-file counts). Four lanes green; player + editor smoke
  with the walk and with a bogus `--data-root` (refused, exit 1).

## WebGPU blit-capable formats (2026-09-16, from the Beef port's WebGPU WIP)

They flagged, rather than buried, that IsBlitCapableFormat excluded BC but let ASTC fall
through to "renderable". Real: a mip-chained ASTC texture (the mobile web content path) had
RenderAttachment widened onto it and would fail creation; the 8-bit snorm formats had the same
hole. Now an allowlist of WebGPU core's renderable colour formats (default = not capable) with
a predicate test over every enumerator plus a live-device no-op pin. The lesson from the
Texture audit again: a mapping switch's `default:` is a suspect.

## Ring flush + bone pool (2026-09-16, from the Beef port's WebGPU profiling)

Their profile of RenderStressTest on their WebGPU backend found ~145 MB of memcmp per frame:
every DynamicUniformRing mapped and unmapped each frame, and an emulated mapping compares the
whole shadow on Unmap even when nothing wrote it (bones.staging alone is 128 MB). Same code
here. Built: `rhi::Buffer::FlushRange` (default no-op; WebGPU uploads/compares only the window
and Unmap after it sends nothing), rings map lazily on first allocation and flush only their
written slots; the bone pool starts at 4096 slots and grows in-frame (power of two, capped at
the old 1M) instead of reserving 256 MB up front. Four lanes green; WebGPU stress run clean.
Not measured here (their number is theirs); the pins are upload counts, not timings.

## Caster-list downcast by renderer id (2026-09-16, Beef port finding)

Real UB: BuildShadowCasterList treated rendererId 0 as "is a MeshRenderData", but 0 is only the
first-registered renderer - the terrain probe registered terrain alone and read bones out of
terrain fields every shadowed frame. Fix, chosen for external-renderer extensibility (user:
"we need to support adding external renderers - don't break that"): a `RenderDataKind` byte on
the base stamped by MeshRenderData's constructor (subclasses inherit; external data is Generic),
the caster list gates on it and drops its BatchKey recompute (extraction already stores the same
key). The particle mesh sets stamped a literal id 0 too - now `RenderSubsystem::MeshRendererId()`.
Regression test registers an external renderer first; verified failing on the old gate. Four
lanes green. RULE: never infer a RenderData's concrete type from rendererId; ask `kind`.

the old `dfSize` key; six UIDocumentAssets v0 with the retired inline `markup`; six

worker). ASAN cook of PaperKid: clean, no leaks. Tests: concurrent RegisterCoreTypes, concurrent
TypeRegistry::Register, concurrent MarkupLoader::Initialize, the sample-project cook. Four lanes
153/153. Docs: paperkid.md recipe, editor.md headless flags.
