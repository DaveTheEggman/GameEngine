# Parity check: Draconic vs LumixEngine vs Traktor (2026-08-10)

Full surveys: Lumix on branch `lumscript` (HEAD 9428a1a06, 2026-08-07),
Traktor at acde828f7 (2026-08-09), Draconic at 0a45edce. Both references are
actively developed, mature (10-20 year) engines. Ours is ~1 year old, which
frames the result: CORE ARCHITECTURE at or ahead of parity, CONTENT-SYSTEM
BREADTH behind both, EDITOR at genuine parity, agent/testing/web capabilities
ahead of both.

## The gap list, ranked (proposed track order)

P0 - the three known gaps, ordered by value-per-effort:
1. PROPERTY ANIMATION (smallest, pure play to our strength): a
   PropertyTrack keyed on reflected properties (float first, then
   Vec/Color/enum via Variant) + a `PropertyAnimatorComponent` + editor
   curve page. Lumix's shape (`property_animator`: reflected Property<float>
   per curve + transform channels + looping) is the proven minimal design.
   Unlocks: gameplay polish now, the SEQUENCER later (Traktor Theater =
   acts of property tracks over time - same substrate).
2. NAVIGATION: vendor Recast/Detour (both references do; full-tree vendor
   per house rule). Zone-based like Lumix (`navmesh_zone` extents + agent
   params + async bake with progress + partial tile rebuild), agent
   component with Detour crowd avoidance, debug draw, cook the zones.
   Physics/scene integration seams exist.
3. TERRAIN (largest; renderer + editor + physics + pipeline): heightfield
   asset + splat material + brush editor (elevate/flatten/smooth/paint;
   Traktor's brush architecture is the richer reference), grass layer,
   Jolt heightfield shape, terrain cast-shadows. Defer ocean/river/forest.

P1 - next tier once P0 lands:
- Mesh LOD (Lumix: 4 LODs + auto-LOD at import via meshoptimizer - we
  already vendor nothing for this; evaluate) + impostor baking later.
- Animation upgrades on the existing graph: state-machine layer (Traktor
  compiles StateGraph -> runtime; Lumix executes graph directly - ours can
  extend the graph), IK node, root motion, bone masks/layers.
- Ragdoll + vehicles (Jolt has both natively - smaller than it sounds).
- Particles: ribbons/trails + mesh particles (Lumix parity), then the
  planned GPU sim (leapfrogs both).
- Audio P2 (spec exists): spatialization polish, filters, banks.
- Post additions: DOF, motion blur, film grain (motion vectors exist).
- Volumetric fog (Traktor has elevation-aware; we have analytic sky only).
- Async loading (task #123) + background cook w/ file watcher (Lumix
  asset_compiler pattern).
- Editor steals: ImGui-Test-Engine-style scripted editor smoke tests on
  our toolkit; asset browser thumbnails + multi-select-edit; entity
  folders in hierarchy.

P2 - mature-engine breadth (schedule on demand):
- Upscalers: FSR3 (open SDK) behind a RenderPlugin-ish seam; DLSS only if
  a real need appears (SDK friction).
- GI/baking: embree-based lightmap/irradiance bake (Traktor path), or
  our planned probe evolution; hardware RT is native-only (WebGPU-first
  constraint says keep it optional).
- Sequencer/cutscenes over property tracks (Theater analog).
- Large-world: double-precision positions + camera-relative rendering
  (Lumix does this throughout) + world partitions/additive scene loading.
- I18N (Traktor has a full module; we have nothing - editor font is
  Latin-1-only today, so this is font + string-table work).
- Video playback (Theora is the no-dep-friction codec both-ways).
- Distributed pipeline cache (Avalanche analog; our deterministic cook
  fingerprints make this natural).
- Crash reporting (Lumix: dbghelp + stack trees).

## Where we are ahead - protect these
1. Web as a first-class platform (wasm + WebGPU + web player + export).
2. RHI multi-backend with validation + Null layers.
3. Scripting architecture (backend-neutral + battery + reflection-driven +
   typed decls + debugger) - both competitors' weakest-vs-us area.
4. Reflection system (domains, borrow modes, containers, RESOLVE) - powers
   inspector/serialization/scripting/MCP from ONE mechanism (Lumix needs a
   custom annotation code generator for the same).
5. MCP/agent access plan v2 + testing rigor (sanitizers, goldens, tripwires).
6. In-engine replication.
7. Text scenes + wire-versioned prefabs.
8. VG/MSDF UI quality stack.

## Honest caveats
- Both references RUN SHIPPED GAMES; our breadth numbers are younger and
  several "parity" rows have thinner mileage behind them.
- Lumix's LumScript investment (~1100 file-touches/6mo) means their engine
  feature velocity is currently LOW - a window, not a moat.
- Traktor is one veteran developer with 20 years of accumulated systems -
  breadth parity is a multi-year horizon; pick gaps by GAME need, not by
  checklist completion.
